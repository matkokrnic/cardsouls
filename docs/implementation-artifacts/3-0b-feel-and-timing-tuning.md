# Story 3.0b: Feel and timing tuning

Status: ready-for-dev

## Story

As a solo developer building CardSouls,
I want the melee combat loop's timing, movement, and legibility judged and tuned against the real skinned rig delivered in 3-0a,
so that the five DEBT E judgments and the 3-0a live-smoke findings are resolved with logged verdicts, and combat reads correctly to a naive observer, before the card system builds on top of it.

## Acceptance Criteria

1. **Delivered in Pass 1 (2026-08-02).** Deterministic step/pause exists for a running match. While paused, four things freeze: `_match_state.set_camera_basis()` (both per-slot pushes), `_gather_contact_facts`, `_match_state.advance()`, and both `HeroActor.drive()` calls; camera FOLLOW (the split-screen viewport mirror, step 4b) keeps running — harmless, and the operator must be able to look around while paused. The camera-basis push rides inside the freeze despite being provably inert while paused (the stepped tick re-pushes the live rig basis before `advance()` next reads it) — this AC describes DELIVERED software, so the freeze list matches what actually ships, not the minimal set that would suffice. Single-step advances exactly one tick per press, performing the normal per-tick order exactly once: gather camera basis -> gather contact facts -> advance -> drive. Step/pause is a match-global DEBUG input, not an intent: it never enters `InputIntent`, never enters the recorded intent stream, and never passes through `advance()` — a deliberate divergence from `debug_reset` (which IS intent-carried, per its own ruling), because pause must survive the absence of ticking, which an intent (consumed only inside `advance()`) cannot do. Controller SAMPLING is explicitly NOT frozen — a named limitation, see Dev Notes. The step/pause Input Map actions land in this story and only here — the E3 revisit gate scoped this rule: card-play actions belong to 3-5. `project.godot` edited textually with the editor closed, diff reviewed.

- **AC7 VERDICT: KEEP the instant block entry pop.** The deciding reason is not generic input latency — `enter_block()` opens the 9-tick (0.15s) deflect window on the entry tick itself, so a 0.05s blend would cover a THIRD of that window (0.1s would cover TWO THIRDS) with a "shield still rising" pose on screen.
